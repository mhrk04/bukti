## Findings

### [HIGH] CSO-001: Unauthenticated claim verification enables provider-cost exhaustion

**Confidence:** 9/10  
**Phase:** Phase 1 / Phase 9 — Attack surface and OWASP A04/A06  
**Category:** Availability / resource abuse  
**Location:** `web/src/app/api/check/route.ts:7-29`

**Description:** `POST /api/check` accepts any anonymous caller after only a 4,000-character input check. Each accepted request can trigger one URL fetch, two Tavily searches when configured, and one request per configured Gonka model. No authentication, IP/user rate limit, quota, concurrency cap, cache, or abuse challenge exists in the repository.

**Exploit scenario:** An attacker scripts repeated POST requests with distinct claims or public URLs. The deployment performs the external Tavily/Gonka work for every request until provider quotas, serverless concurrency, or request budgets are exhausted. A public deployment can therefore be degraded or incur unbounded third-party usage costs without owning a wallet.

**Evidence:** The route calls `checkClaim(claim.trim())` directly at line 21. `checkClaim` performs `resolveEvidence` and `resolveTrustedSources` in parallel at `web/src/lib/gonka.ts:231-234`, then calls every configured model at `web/src/lib/gonka.ts:255-262`. Repository-wide search found no rate-limit, quota, 429, or middleware implementation.

**Remediation:** Add a deployment-level rate limit and quota before `checkClaim` runs, keyed by IP plus a durable client/session identifier. Return `429` with `Retry-After`; cap concurrent checks and apply a daily provider budget. If the endpoint is intended only for connected users, require a short-lived server-verifiable wallet/session token rather than relying on the browser UI.

**Priority:** P1 (fix this sprint; immediately before public launch)

**Status:** Mitigated in the working tree with shared per-IP request limits, per-instance concurrency caps, and `429` responses. A shared edge limiter is still required for strong multi-region enforcement.

### [HIGH] CSO-002: Unauthenticated Walrus publisher route enables storage/cost abuse

**Confidence:** 9/10  
**Phase:** Phase 1 / Phase 9 — Attack surface and OWASP A04/A06  
**Category:** Availability / resource abuse  
**Location:** `web/src/app/api/publish/route.ts:30-89`

**Description:** `POST /api/publish` is publicly reachable and authorizes no wallet, signature, session, or quota. It accepts any valid JSON object with `version: 1` up to 200,000 bytes, uploads it to permanent Walrus storage, reads it back, and returns a blob ID. The browser disables this action unless a wallet is connected, but that is not an authorization boundary.

**Exploit scenario:** An attacker sends direct HTTP requests containing minimal `{"version":1}` or larger valid JSON bodies. Each request causes a publisher PUT and aggregator read, consuming the deployment's Walrus resources and request time. Repetition can exhaust platform concurrency or create unbounded storage/provider usage without paying gas or connecting a wallet.

**Evidence:** `web/src/app/api/publish/route.ts:30` exports an unauthenticated POST handler; validation at lines 51-65 checks only JSON parsing and the version marker; `storePermanentBlob(bytes)` is called at line 70. `web/src/app/WalletApp.tsx:142` only provides client-side gating and does not protect the route.

**Remediation:** Require a server-verifiable authorization token tied to the wallet/user, or move the Walrus upload to a signed/short-lived upload flow. Add strict rate and storage quotas, reject payloads that are not the expected canonical schema, and enforce an application-level maximum lower than the transport ceiling. Keep the wallet UI check as usability, not security.

**Priority:** P1 (fix this sprint; immediately before public launch)

**Status:** Mitigated in the working tree with shared per-IP request limits, per-instance concurrency caps, deterministic canonical serialization checks, and strict schema/field bounds. A server-verifiable wallet/session authorization remains the stronger production control.

## Defense-in-depth observations

- No dependency vulnerabilities were reported by `pnpm audit --json` (0 low/moderate/high/critical across 115 dependencies).
- `pnpm typecheck`, 35 web self-checks, `sui move build`, and all 6 Move tests passed.
- SSRF defenses are present for direct evidence retrieval: scheme/credential checks, DNS private-address rejection, manual redirect validation, content-type checks, body limits, and timeouts. A future hardening pass should pin the resolved address or use an SSRF-aware egress proxy to close DNS-rebinding races.
- `web/.env.local` and `.env.local` are ignored and absent from Git history checked by this audit. They contain live-looking local credentials; rotate them if the files were ever shared or backed up outside the trusted machine.
- No `.github/workflows` or Docker configuration was found, so CI/CD and container controls could not be assessed beyond confirming their absence.
- The Move publishing functions are permissionless, but they only create frozen public receipts and do not expose mutable privileged state; this matches the documented product model and was not classified as a vulnerability.
- No user-controlled HTML injection, command execution, SQL, webhook, or private-key handling path was found in the audited source.
